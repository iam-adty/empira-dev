# AGENTS.md

> **Working notes for the application.** Framework guidance lives in
> [`principle.md`](principle.md) — do not duplicate it here.

`iam-adty/empira-app` — a **bare skeleton**: the smallest application that boots
and serves, and the answer to "how do I wire this up?".

## Commands

```bash
composer serve                      # http://localhost:8000
vendor/bin/empira migrate           # the schema, before anything serves
composer validate                   # must stay clean
```

There is no `seed` command, and there is no test suite here either. See
[Account switching](#there-is-no-seed) below, and
[The skeleton ships no tests](#the-skeleton-ships-no-tests).

## Layout

```
app/
├── composer.json      requires empira-principle and empira-auth, both from GitHub
├── composer.lock      committed: an application pins its build
├── docker-compose.yml nginx + php-fpm + PostgreSQL, no image build
├── docker/nginx.conf  bind-mounted into stock nginx
├── migrations/        empty, on purpose — see the .gitkeep
├── bootstrap/app.php  what `bin/empira` boots
├── bootstrap/modules.php  what this application is made of
├── public/index.php   front controller, classic runtimes only
└── src/
    ├── App.php        all the wiring, in one readable method
    ├── Layouts/       SiteLayout — the document and its regions
    └── Pages/         HomeLayout — the one page
```

## The skeleton ships no tests

It did, and that was a defect rather than a convenience. The suite, `tools/test`,
`phpunit.xml`, a `require-dev` on phpunit and a `composer setup` script all lived
here — and `composer setup` called `empira seed`, a command this application never
had, while `AppTest` asserted that the application registered **no commands of its
own**. A manifest contradicting its own suite is worse than a missing feature,
because `composer setup` is the first thing anyone runs on a fresh clone.

All of it now lives in `app-test/`, a scratch application generated by
`dev/tools/app-test` from this repository's own GitHub clone plus the overlay in
`dev/app-test-harness/`. It is disposable: edit it, and `reset` throws it away.
The suite that ships is 20 tests — the 16 that were here, plus 4 for the seeder,
which the skeleton cannot have.

```bash
dev/tools/app-test create   # build app-test/ from app + the harness
dev/tools/app-test check    # run its suite
dev/tools/app-test reset    # throw it away and build it again
```

The one consequence worth knowing: because the suite is generated from a *clone*,
a change to `app/` is not covered until that change is pushed and the scratch app
rebuilt. `APP_REPO=../app dev/tools/app-test check` builds from the working tree
instead, which is how you test a change here without pushing first.

`dev/tools/module-contract` enforces all of this — no tracked tests, no phpunit in
`require-dev`, no `autoload-dev`, no `test`/`setup`/`seed` scripts, none in the
lock. Adding a suite back to the skeleton fails the contract rather than quietly
re-growing the thing this was meant to prevent.

Scratch space is `../tmp`, above every package rather than inside one, and it is
mounted into every container — so `dirname(__DIR__, 2) . '/tmp'` reaches the same
place from the host and from inside the runner, in `app-test/` and in `app/`
alike. Nothing in `/tmp` ever holds a fixture.

## This is a skeleton on purpose

It used to be a demo: sign-in, registration, a dashboard, rate limiting, a nav
bar, eight components, four layouts, four pages, and a seeder. All of that is
gone.

Not because it was wrong, but because a skeleton you copy arrives with someone
else's decisions already made — a rate limiter you did not ask for, a session
strategy you now have to unpick, a `users` table seeded with credentials on
first boot. Every one of those is a thing to *remove*, and removal is slower
than never having it. What is left is a boot method you can read in one sitting,
a page, and a layout.

The trade is real and worth stating: **this app no longer demonstrates what the
framework can do.** The auth module's own suite demonstrates authentication; the
framework's 473 tests demonstrate components, routing, regions, sessions, CSRF
and the ORM. If you want a worked example of a feature end to end, read that
package's tests rather than looking for it here.

## The two lines that matter

Everything an application needs beyond the obvious is these two, and they are
meant to be read together:

```php
$app->orm(self::databaseConfig(), [__DIR__, AuthModule::entityPath()]);

$app->module(new AuthModule([
    new SessionGuard($app->session(), new DoctrineUserProvider($app->entities())),
]));
```

**Drop both and you have an application with no authentication** — which is the
point. Authentication used to be inside the framework, which meant every
application carried a users table whether it asked for one or not. It is a module
now, and asking for it is a line you can delete.

**Do not drop one without the other.** A module with no mapped entity cannot
read a user. A mapping with no module maps a table nobody asks anything about.

## `AuthModule::entityPath()` is load-bearing

Doctrine separates **discovery** from **lookup**. `getClassMetadata(User::class)`
reflects on the class you name, so it works whether or not `User`'s directory was
registered — which means forgetting the entity path changes nothing at request
time, and 14 of this app's tests passed without it.

What breaks is `getAllClassNames()`, which is what the **schema tooling** reads.
The failure of a missing path is not an exception; it is a `SchemaTool` quietly
generating DDL that omits a table an entity depends on.

`testTheModuleEntityDirectoryIsDiscoveredNotMerelyReachable` asserts on the
discovery half, and exists for exactly that reason. If you add an entity in
another package, that test is where the path gets registered.

## Migrations

`migrations/` is **empty, and that is intentional**. `empira migrate` refuses to
run without the directory — correctly, since a project with no migrations should
be told so rather than having the command report success against a directory it
never found.

The migrations that are real come from modules:

```
Empira\Migrations\Auth\Version20261011000001   auth/migrations
Empira\Migrations\Auth\Version20261012000001   auth/migrations
```

A module registers its migration directory at boot, and `migrate` plans across
all of them in one sequence against one version ledger — so ordering between a
module's table and your column on that table has one answer. Drop a
`Version*.php` in `migrations/` and it is sequenced alongside them, not after.

Each module's directory needs **its own** namespace, matching the `namespace`
line inside its files. Sharing the project's `Empira\Migrations` means two files
declaring the same class name, and which one Doctrine runs depends on which
`require` reached the definition first.

## There is no seed

The seeder is gone, and nothing in this repository calls one. A skeleton has no
accounts to invent, and **a deploy step that seeds demo credentials into anything
reachable is the wrong default to ship in a file somebody copies.** There is no
`docker/entrypoint.sh` to add one back to either — the runtime is stock nginx and
php-fpm with no image to build.

The one that does exist is [`app-test/src/SeedCommand.php`](../../dev/app-test-harness/src/SeedCommand.php),
in the generated scratch app, registered from its `bootstrap/harness.php`. That is
where a seeder belongs in this workspace: **outside the thing that ships.**

If you add one to a real application, register it at boot the same way — but in
your own bootstrap, not inside `App::boot()`, so that `App.php` stays a readable
wiring file rather than a place commands accumulate:

```php
// bootstrap/app.php
$app = App::boot(csrf: false);
$app->command('seed', new Seed($app->entities()));

return $app;
```

Make it idempotent — a deploy step is allowed to be run twice, because a retried
pipeline should not fail on a seed that already happened.

## What the suite covers, and why it is small

It went from 45 tests to 16 because most of them tested features that no longer
exist, and then to 20 when the seeder's four came with it. A test for a feature
nobody ships is a test nobody reads and a suite that fails for reasons unrelated
to what it is meant to catch.

What is left is the question a skeleton actually has to answer: *does this boot,
and does it serve?* — the page renders, an htmx request gets only its region, an
unknown route 404s, the error view does not change the status, the module
installs and publishes its façade, its table arrived without an application
migration, the entity directory is discoverable, the secret guard guards, and
`migrate` is idempotent.

Nothing here should stop you adding a test. The rule is narrower than it looks:
**a test for a feature this skeleton has must live in `app-test/`, not here.**
`testBootingRegistersNoCommandsOfItsOwn` asserts that boot registers nothing, so a
command that should not be in the skeleton cannot quietly return — and
`dev/tools/module-contract` is what stops the `seed` script coming back with it.

## The libraries are installed, not linked

Both dependencies resolve from GitHub through Composer `vcs` repositories:

```json
{ "type": "vcs", "url": "git@github.com:iam-adty/empira-principle.git" }
{ "type": "vcs", "url": "git@github.com:iam-adty/empira-auth.git" }
```

A path repository used to sit here too, so a sibling checkout resolved without
the network. It was removed because it does not survive a clone — the whole
point of a public repository is that someone can get this working from nothing
but the URL. It also took `franzl/studio` with it, since studio exists only to
maintain symlinks.

**Consequence: an edit under `principle/src` is no longer live by default.** It
reaches this application through `composer update iam-adty/empira-principle` and
a new push. That is deliberate — the container runs what `composer.lock` pins, so
it and the host cannot quietly disagree about which version of a library is
running.

**To develop a library against a running container**, put this in
`docker-compose.override.yml` (gitignored, loaded automatically):

```yaml
services:
  app:
    volumes:
      - ../principle:/workspace/app/vendor/iam-adty/empira-principle
      - ../auth:/workspace/app/vendor/iam-adty/empira-auth
```

**The lock is what moves the pin, not a rebuild.** After a library change is
pushed, this application's install still holds the old commit until you run:

```bash
cd app && composer update iam-adty/empira-principle iam-adty/empira-auth
```

The Docker build reads the lock, so a library change that has not been `composer
update`d here is simply not in the image — and the build will not tell you, which
is correct: an application that picks up a dependency's `main` on its own is not
reproducible.

**Mount each package whole, not `src/`.** They used to be mounted in the
committed compose file, source directory only, and that produced a package split
down the middle: classes from the working copy, `migrations/` from the image. A
new class arrived instantly while the migration creating its table did not, and
the failure appeared at query time with nothing to point at a mount. Proved by
appending a line to a migration and finding the container did not see it.

**The image still installs from path packages**, because the build context is the
workspace root and both siblings are in it — so the build needs all three
repositories side by side, and the guard in the Dockerfile says so rather than
failing with a bare `COPY failed`.

## Things that will bite you

- **A region gets its id from `$region->element()`, not from what your callback
  returns.** Returning a plain `$this->hx->div()` renders a div with no id, so
  `hx-target` finds nothing and an htmx swap silently targets nothing. The id is
  `region-<name>`, so target `region-main`, not `main`.
- **`App::boot()` runs per php-fpm worker.** It does not migrate and does not seed,
  and that is deliberate: a boot that migrates has every worker racing through the
  same migration. The `php` service migrates once, before php-fpm starts.
  Do not move either back into boot.
- **The `SessionGuard` must be built from `$app->session()`** — the application's
  own session, the one everything else writes to. A guard holding a session of
  its own reads a store nobody writes, and every sign-in fails as "wrong
  password". It looks correct in review because the type is right.
- **`send()` in the front controller, `respond()` in a worker.** `send()` exits,
  which takes a worker down and earns you one request per process. This
  application calls `send()` and has no branch: worker mode is a package
  (`empira-frankenphp`) whose `worker.php` calls `respond()` in a loop. If you add
  a loop here, you have re-added a runtime the application does not use.

## `APP_SECRET`

`.env.example` ships a **demo placeholder**. Generate your own for anything real:

```bash
php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'
```

It must be at least 16 bytes, and must not change between deploys — changing it
invalidates every component link already in a user's history.

`App::boot()` **refuses to start** on the placeholder unless the environment is
local. The failure this guards against is silent, which is why it is a boot check
rather than a log line: a component token is
`base64url(payload).base64url(hmac)` and the payload carries the component class
and its props, so with the secret in the open anyone can mint a signed URL for
any component with any props they like. Nothing 500s, nothing is logged, and the
forged URL simply works.

**It is opt-in, and that is worth being plain about.** An unset `APP_ENV` counts
as local, so the guard fires when somebody sets `APP_ENV=production` and forgets
the secret — *not* when they set neither.

## Before committing

```bash
composer validate
APP_REPO=../app dev/tools/app-test check   # the suite, from the working tree
dev/tools/module-contract                  # the skeleton is still bare
```

If you changed the framework or the auth module, test those too — they are
separate packages with their own suites:

```bash
cd ../principle && composer test
cd ../auth && composer test
```

The middle command rebuilds `app-test/` from this directory rather than from
GitHub, so it covers a change that is not pushed yet. `dev/tools/app-test` with no
`APP_REPO` set clones from GitHub instead, which is the honest check of what a
consumer gets — and is how you find out that `app/` is not actually installable.
